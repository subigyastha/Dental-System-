ClinicFlow phase review

Current review: Phase 1 — Protected application boundary

Reviewed: 2026-07-18 • Decision: IMPLEMENTED — CI INTEGRATION PROOF AND VISUAL DEMO PENDING

The uncommitted Phase 1 changes materially improve Nest route protection and remove the workspace’s direct-data/seed fallback. Exact public-action binding, focused security middleware tests, targeted tenant-scoping tests, a CI-only HTTP integration harness, and deterministic workspace-boundary tests are now in place. The HTTP harness is intentionally pending its ephemeral PostgreSQL CI run because no disposable local database exists; that is pending execution evidence, not a known code defect. Formal phase closure still requires that CI result and the required browser/API demonstration. Cookie sessions and CSRF are expected P2/UP-02 work, separately recorded below; their deferral still blocks a production release but is not presented as a Phase 1 containment regression.

IMPLEMENTED FOR CHANGED PATHS Changed services now resolve the user session and query by its organization: Organizations, Follow-ups, Communications, System status, and operational data. Communications also rejects a body client ID that does not match the scoped appointment.
Anonymous and cross-tenant requests fail across every current module without identifier leakage. PARTIAL / TARGETED PROOF The 11-test focused suite now covers tenant scope for Organization update, Communications, Follow-ups, operational data, and System status through phase-one-tenancy.spec.ts; customers.tenancy.spec.ts adds two Client cases. This is good evidence for the known exposed paths, but it is not yet a real HTTP/disposable-database denial matrix for all 12 legacy modules or a full identifier-leak assessment.
Known Phase 1 exposed paths are denied anonymously and scoped across organizations through a real Nest HTTP server. CI-PENDING PROOF phase-one-http.integration.spec.ts starts Nest against TEST_DATABASE_URL, creates two synthetic clinics, proves anonymous 401s and cross-clinic 404s for Organization, Communications, and Follow-ups, and verifies the scoped operational/system reads do not change Clinic B. It refuses to use DATABASE_URL or an .env fallback; it requires a named test/CI/sandbox database. The local clean run correctly skipped because no disposable database was configured. CI supplies an ephemeral migrated PostgreSQL service through TEST_DATABASE_URL; its green result is still required evidence.
Workspace does not read Prisma/seed data when the secure API is unavailable. IMPLEMENTED FOR WORKSPACE BOOTSTRAP workspace layout no longer calls getOperationalData; WorkspaceRoot loads Nest /operational-data and renders a retryable unavailable state. database-data.ts is type-only. Three deterministic workspace-boundary tests cover redirect before clinic rendering, unavailable-without-sample-data, and ready only after authenticated data. The focused boundary check passed and reports four known migration paths remaining.
No direct Next.js Prisma operational authority remains. DEFERRED TO P2 / UP-04 The boundary check is a regression guard, not proof of removal: its allowlist explicitly permits legacy paths. In particular web auth and Next login still use Prisma, and the staff workspace still calls legacy Nest /api/operational-data rather than the future scoped /api/v1 read models. The four disabled Next operational routes are a useful containment measure, not the completed API-boundary migration.
Security headers, CORS restrictions, rate limiting, and correlation IDs are present. IMPLEMENTED BASELINE main.ts adds CORS allowlists, several response headers, request IDs, and an in-memory login/API rate limiter. http-security.spec.ts proves production-origin defaults, header/correlation-ID behavior, and the login 429 threshold. The in-memory limiter and end-to-end correlation propagation remain later distributed-runtime work, not an untested P1 claim.
Secure server sessions, HttpOnly cookies, CSRF, rotation/revocation/logout, and no browser token storage. DEFERRED — P2 / UP-02 Nest AuthService still signs stateless HMAC bearer tokens with a fallback secret; the web login page stores the token in localStorage; api-client.ts sends an Authorization: Bearer header. There is no session table, cookie, CSRF proof, revocation/rotation, logout endpoint, or production secret fail-fast validation. This is an explicit release blocker, not a cosmetic follow-up.

Actual Phase 1 risks and required closure work

  1. Wait for the CI job to complete the migrated ephemeral-PostgreSQL HTTP harness. This is pending proof, not a known local code defect; do not substitute a developer or deployed database to make the test run locally.
  2. After CI proves the five known exposed paths, expand the disposable-database HTTP denial matrix to all legacy modules and prove 401/403/404 responses do not reveal cross-clinic IDs or counts. The current 13 focused tests plus one CI harness are not yet a complete module matrix.
  3. Run the signed-in, anonymous, API-outage, and cross-clinic browser/API demonstration using synthetic fixtures, then attach redacted evidence below. No browser capture was available during this review.
  4. Before distributed deployment, replace the process-local rate limiter and propagate correlation IDs through structured logs, audit records, traces, and worker boundaries.

Expected Phase 2 / later deferrals

These items are intentionally not treated as Phase 1 defects. They remain production-release blockers until their scheduled phases complete.

  • P2 / UP-02: replace browser-held HMAC bearer credentials with server-side sessions, secure HttpOnly cookies, CSRF protection, expiry/rotation/revocation/logout, and startup secret validation.
  • P2 / UP-04: retire temporary Next Prisma auth routes and legacy /api/operational-data, then deliver scoped /api/v1 read models as the sole web operational boundary.
  • P7: replace process-local rate limiting with shared infrastructure and propagate correlation IDs through structured logs, audit records, traces, and worker boundaries.
